## Что проверяет workflow

- Только ручной запуск в публичном диагностическом репозитории, стандартный ubuntu-24.04, contents read, checkout с закреплённым commit без сохранения credentials. Host получает QEMU и ISO tools из официальных Ubuntu repositories и сверяет подписанный SHA256SUMS cloud image. В гостя передаётся проверенный образ и один нейтральный CIDATA ISO. Содержимое ISO — meta-data, network-config, neutral.txt и user-data с этим диагностическим скриптом. Драйверы Q5/Q6, credentials и закрытый код отсутствуют.
- Гость Ubuntu 24.04 x86_64, 2 vCPU, 2048 MiB, KVM без fallback. Один writable qcow2 без backing file и один read-only CD-ROM. Запуск с фиксированным списком параметров без пользовательской конфигурации, NIC, monitor, QMP, графики, USB, forwarding, host sockets, virtiofs, 9p и дополнительных назначенных устройств. Гость сверяет PCI-инвентарь q35, блочные устройства, mount types, отсутствие признаков virtio-serial, vsock, USB и известных agent units. Неожиданный инвентарь приводит к FAIL. Разрешённые направления записи из гостя — его временный диск и serial output в однонаправленный pipe супервизора. Нет интерактивной host-консоли или файлового обмена. Это проверка конфигурации, без гарантии против уязвимостей гипервизора.
- В госте отдельно проверяются результаты обоих вызовов ip, затем только lo, отсутствие default и маршрутов через другие интерфейсы. Host конфигурация -nic none дополняет guest observations.
- Host перечитывает инвентарь и байты всех четырёх файлов из ISO. Сверяются SHA‑256 полного ISO и SHA‑256 канонического списка хешей файлов. Гость читает ISO поблочно с /dev/sr0, сверяет точный инвентарь и монтирует iso9660 с ro,nodev,nosuid,noexec. Открытие существующего файла на запись и эксклюзивное создание нового должны вернуть EROFS. Повторное хеширование подтверждает неизменность файлов. Хеши, наблюдаемые гостем, принимаются только при точном совпадении с host.
- Проверяются инструменты, root tmpfs /run, действительный синтаксис sudoers, конфликты UID/GID, создание и удаление qa и двух синтетических групп. Проверка abort при отсутствующем getfacl или другой необходимой утилите. Пакеты в гостя не устанавливаются и сеть гостя не добавляется.

## Приёмка будущего запуска

**1200 с** — монотонный дедлайн принятия успешного решения супервизором, отсчитанный от начала VM-фазы. До 1170 с нужен штатный выход QEMU. Резерв до 1180 с для остановки и сбора прямого потомка, до 1187 с для serial проверки, до 1195 с для штатного rm, до 1198 с для TERM/KILL, сбора rm и проверки отсутствия каталога. До 1199 с зарезервировано для сбора процесса проверки, остаток — для финального решения. **30 минут** — отдельный максимальный timeout GitHub Actions job, включающий подготовку и VM-фазу. Синхронные операции после решения, включая закрытие дескрипторов и вывод результата, теоретически могут задержать фактический выход процесса. Дедлайн решения не доказывает жёсткую внешнюю отсечку всей VM-фазы. Если процесс не собран, рабочие файлы не удаляются супервизором, результат QEMU_STOP_UNCONFIRMED. При штатном выходе 0, точном единственном маркере гостя, последующей строке штатного выключения и подтверждённой очистке до дедлайна ожидается OFFLINE_ISO_READY и код 0. Отмена, отказ команды, неподтверждённая остановка или опоздание исключают успех. Жёсткое уничтожение runner может оставить очистку неподтверждённой.

Сохранять в отчёте только run ID/attempt/commit, версию QEMU, KVM API, image/ISO/manifest hashes, фиксированные маркеры, длительности, код и статус очистки. Serial собирается в памяти во время работы QEMU. В буфере не более 8 MiB. Следующий байт вызывает SERIAL_LIMIT_EXCEEDED и остановку с подтверждением сбора процесса. Сырые данные не записываются на диск и не выводятся в Actions. Артефакты отсутствуют. Хеш ISO вычисляется для конкретного запуска. Сборка ISO может включать метаданные времени.

До фактического запуска нужны независимый статический review, отдельное разрешение на публикацию и один ручной запуск, проверка точных публикуемых файлов и SHA, допустимости стандартного публичного runner и отсутствия закрытых материалов. Первый запуск проверит совместимость фактического Noble image, ISO reader, q35-инвентаря и набора утилит. При расхождении остановиться без расширения разрешений или повтора. Позднейшая адаптация настоящего A–D требует отдельного согласования доверенной консоли, приватного переноса материалов и наблюдения. Этот workflow для такой передачи не предназначен.

## Отказы очистки

Супервизор запускает rm через execve в прямом дочернем процессе с отдельным PGID. Перед удалением проверяются исходные device/inode собственного временного каталога. После кода rm 0 отсутствие каталога подтверждается lstat в отдельной ограниченной фазе. Опоздавший или ошибочный rm, оставшийся каталог и неподтверждённый сбор исключают успех. Код 22 обозначает исчерпанный бюджет, код 25 — неподтверждённый сбор rm или ошибку его супервизора. Код 21 обозначает ошибку rm или проверки отсутствия каталога. При одновременных ошибках отметки фаз сохраняются. Неподтверждённая остановка QEMU (23) имеет приоритет, иначе переполнение serial сохраняет код 24 даже при последующем отказе очистки.

Локальные заглушки не подтверждают поведение stdio backend QEMU на Actions. При SIGKILL супервизора, аварии runner или неотзывчивом ядре подтверждение остановки и очистки может отсутствовать. Успех требует наблюдаемого завершения и проверки в пределах общего бюджета.

## Финальный аудит идентичности очистки

Действует модель доверенного одноразового GitHub-hosted runner. Враждебный процесс с UID runner и его passwordless sudo считается компрометацией хоста. Preflight проверяет тип, владельца, режим 0700 и канонический путь родителя. Сразу после mktemp workflow сохраняет dev:ino. Супервизор принимает только каталог с ожидаемым именем непосредственно в RUNNER_TEMP и сверяет исходный dev:ino до запуска VM. Подготовительная ловушка не удаляет каталог по строковому пути.

Супервизор удерживает дескрипторы родителя и исходного рабочего каталога до итогового решения. На Linux используется O_PATH вместе с O_DIRECTORY, O_NOFOLLOW и O_CLOEXEC. После fork дочерние процессы сразу закрывают копии этих дескрипторов. Проверка перед rm сверяет текущий путь с закреплённым inode. После подтверждённого кода rm 0 требуется отсутствие пути и fstat исходного объекта с теми же dev/ino и st_nlink == 0. Переименование исходного объекта с исчезновением имени не проходит эту проверку. Отсечки 1195/1198/1199 и дедлайн 1200 с сохранены. Ошибка fstat, lstat или потеря идентичности не дают PASS. До запуска VM, перед созданием процесса удаления и непосредственно перед exec проверяется mountinfo. Mount на рабочем каталоге или внутри него блокирует удаление, включая bind mounts с тем же st_dev. Непривилегированный GNU rm дополнительно использует --one-file-system. Между сверкой и exec остаётся окно для процесса, способного менять хост. Это остаточный риск принятой модели, которая опирается на доверие к runner и отсутствие конкурирующих операций в рабочем каталоге.

Локальные тесты используют только собственные временные деревья. На macOS успешная ветка Linux st_nlink == 0 моделируется после фактического удаления тестового каталога, поскольку Darwin сохраняет ненулевое значение для открытого каталога. Отрицательный сценарий с переименованием и сохранённым inode использует фактические fstat и lstat. На macOS inventory mountinfo проверен на синтетических записях, GNU rm заменён локальным адаптером BSD rm только в тестах. Реальная Linux-проверка остаётся NOT_RUN.
